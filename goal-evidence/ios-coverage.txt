iOS request stacks — what they are and how each is reproduced
date: 2026-11-21

question
  "What request libraries exist on iOS, and how do we emulate all their
  versions?"

the libraries, and why most of them share one fingerprint
  iOS apps do not choose a TLS implementation the way Android apps do: most
  get CFNetwork from the platform. So the library list collapses into three
  actual stacks:

  1. NSURLSession / CFNetwork       the system stack. Alamofire, AFNetworking,
                                    Moya, Combine's dataTaskPublisher and every
                                    hand-rolled URLSession call end up here.
  2. WebKit / WKWebView / Safari    WebKit's own stack (Network.framework
                                    under it), so a WKWebView-shaped request
                                    looks different from URLSession.
  3. swift-nio-ssl / NIOSSL         AsyncHTTPClient and the wider Swift
                                    server-side ecosystem link their own
                                    CNIOBoringSSL, so they never touch
                                    CFNetwork. A distinct ClientHello and a
                                    distinct HTTP/2 fingerprint.
  4. Cronet (Chromium's stack), OpenSSL builds and a few SDKs. Each needs its
     own capture; none is here yet.

  "SwiftNIO's URLs" is not CFNetwork, which an earlier revision of this file
  said. NIOSSL links CNIOBorrowSSL (`@_implementationOnly import
  CNIOBoringSSL` in its own sources), so an AsyncHTTPClient app has a
  BoringSSL-shaped hello, not an Apple one. That is now its own record.

the CFNetwork app records carry no OS version
  tls-client files these profiles as `Version: "1"` and every capture's
  request carries the same `CFNetwork/1474 Darwin/23.0.0`, so nothing
  upstream names an iOS release. The records used to say 13.0/14.0/17.0;
  those numbers were shaped from the cipher list, not read from a capture,
  and are gone. The records are addressed by shape instead:
  `fingerprint::distinct_shapes("cfnetwork")` returns 7 stacks.

  NPN works in a stock build
      utls_ios11/utls_ios12 offer NPN (13172). The previous fix added
      `SSL_CTX_set_offer_npn`, which only exists when BoringSSL is rebuilt
      with scripts/boringssl/chrome4832.patch; every default build silently
      dropped the extension while the record still said `exact`. Stock
      BoringSSL already sends NPN whenever `next_proto_select_cb` is set, so
      wreq sets a callback instead and the extension reaches the wire
      everywhere. Regression test:
      tests/wire.rs::ios_11_and_12_carry_the_deprecated_npn_extension.

  a captured SETTINGS frame is sent verbatim
      `SettingsOrder::build()` appended every default id, so a client whose
      capture carries only `3` and `6` also advertised `4:2097152` and its
      Akamai fingerprint could never match. `build_exact()` keeps the captured
      order; prepare.rs uses it. All 4 iOS HTTP/2 records now match their
      captures parameter for parameter, and the other 160-odd records that do
      name `4` are unchanged. Regression test:
      tests/wire.rs::a_captured_settings_order_is_not_padded_with_default_ids.

what cannot be covered, and why
  - There is no iOS 27 capture. tls-client v1.18.1 (and master) tops out at
    Safari_IOS_26_0 and uTLS at iOS 14. A real capture needs an iPhone or a
    macOS host, neither of which this Linux machine can drive. curl-impersonate
    presets do carry Safari 27 for iOS, so `entry_for_version("webkit", "27.0")`
    still resolves - but that is a preset, not a capture.
  - Cronet and apps shipping their own OpenSSL are not represented. Each is
    a distinct ClientHello and each needs a capture from a device.
  - iOS 15-18 app shapes are not recorded separately from 11-14. The
    captures available show the app stack has two shapes (14 and 18
    ciphers), both present; a per-version capture would need real devices.
  - utls_ios11/12 remain HTTP/1.1-only captures (their ALPN is the
    harness's), which is a note on those records, not a missing capability.

how to add more iOS versions
  An iOS ClientHello is reachable four ways, in increasing order of fidelity:
  a ring library's profile (tls-client, uTLS - no device), a Swift package
  built and run here (NIOSSL, which is what the swiftnio_ssl record is), a
  WKWebView on a macOS host pointed at the echo service, or a real iPhone
  with a proxy. This machine is Linux, so the first two are what it can do.
