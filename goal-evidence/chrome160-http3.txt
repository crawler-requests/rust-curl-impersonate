date: 2026-11-17

1. source of the HTTP/3 fields
   binary: Google Chrome for Testing 160.0.8166.0 (linux64), official build
           https://storage.googleapis.com/chrome-for-testing-public/160.0.8166.0/linux64/chrome-linux64.zip
   run:    chrome --headless=new --no-sandbox --disable-gpu --enable-quic \
             --log-net-log=netlog.json --net-log-capture-mode=IncludeSensitive \
             --dump-dom https://quic.nginx.org/
   The NetLog carries the QUIC transport parameters Chromium actually sent on
   a real HTTP/3 connection (QUIC_SESSION_TRANSPORT_PARAMETERS_SENT) and the
   HTTP/3 SETTINGS (HTTP3_SETTINGS_SENT). Two independent runs agree.

   transport parameters sent by Chrome 160:
     max_idle_timeout 30000, max_udp_payload_size 1472,
     initial_max_data 15728640,
     initial_max_stream_data_bidi_local/remote/uni 6291456 each,
     initial_max_streams_bidi 100, initial_max_streams_uni 103,
     active_connection_id_limit 5, initial_source_connection_id 0,
     max_datagram_frame_size 65536,
     google_connection_options ORIG,NOIP (ECCP is added only for Google's own
     hosts: 10 sessions to www.google.com sent ORIG,NOIP,ECCP, while
     quic.nginx.org and update.googleapis.com sent ORIG,NOIP), version_information
     [chosen 00000001 other_versions 00000001], one GREASE parameter.

   The record used to carry only `ORIG` for 12584, i.e. a third of the real
   value; it now records `ORIG,NOIP` (0x4f5249474e4f4950), the value Chrome
   sends to a non-Google origin. The record also had no `14:`
   (active_connection_id_limit) at all, so the peer assumed RFC 9000's
   default 2 where Chrome advertises 5; `14:5` is recorded now. A dump of the
   decrypted Initial confirms `active_connection_id_limit on wire = 5`.

   HTTP/3 SETTINGS sent by Chrome 160:
     SETTINGS_QPACK_MAX_TABLE_CAPACITY 65536,
     SETTINGS_MAX_FIELD_SECTION_SIZE 262144,
     SETTINGS_QPACK_BLOCKED_STREAMS 100,
     SETTINGS_H3_DATAGRAM 1, one GREASE setting.

5. fix: library HTTP/3 profiles were losing the record's TLS handshake
   Before this change `Fingerprint::http3_profile()` built every field from
   the `http3` block alone and defaulted the rest: key_shares was hard-coded
   to `&[]` (so BoringSSL sent no key share at all), and curves, grease,
   alps, ech_grease, session_ticket, permute_extensions, extension order,
   cert compression, delegated credentials and record_size_limit all fell to
   "unset" instead of the record's TLS values. chrome160's profile was
   therefore a QUIC ClientHello with no GREASE, no ALPS, no key share.
   Now every knob falls back to `self.tls` (the same rule curl-impersonate
   uses for http3_curves / http3_sig_hash_algs / http3_tls_extension_order),
   and `Http3Fingerprint::key_shares` exists to override it per record.
   After the fix chrome160's QUIC inputs are byte-identical in shape to the
   chrome152 preset: curves X25519MLKEM768/X25519/P-256/P-384, 2 key
   shares, GREASE on, ALPS on, 17 captured extensions.
   Regression test: tests/fingerprints.rs
   library_http3_profile_inherits_the_records_tls_handshake.

6. trust anchors reach the QUIC ClientHello too
   Http3Profile gained `trust_anchors`, QuicTls::from_profile copies it, and
   Fingerprint::http3_profile() fills it from the record's
   tls.trust_anchors. The wire check below shows extension 51764 in the
   QUIC ClientHello, which previously only the TCP handshake sent.

   Decrypted Initial, chrome160 (tests/wire.rs, wire order):
     27242(GREASE) 17613(ALPS) 43 18 51(key_share) 65037(ECH GREASE)
     16 51764(trust anchors) 0 10 45 13 27 57(QUIC transport params)
     35466(GREASE)
   New test: chrome160_quic_client_hello_carries_key_share_alps_and_grease
   asserts key_share, ALPS, GREASE, supported_versions, a non-empty
   transport-parameters extension and a well-framed 51764 list.

7. HTTP/3 request headers
   Two more defects found while checking the headers:

   a) `policy::negotiated_headers` returned `Some(&[])` (a record with an
      `http3` block but no HTTP/3 headers of its own) verbatim, so the
      request was built with NO headers at all - no user-agent, no accept.
      An empty list now means "use the regular headers".

   b) `Prepared::http3_header_order()` only returned a caller override and
      never the profile's own `header_order`, so a record's HTTP/3 order
      never reached the wire. It now falls back to the profile, and
      `http3_fields()` uses the accessor instead of reading the raw field.

   chrome160's HTTP/3 header order comes from eight real requests in the
   NetLog (all agree):
     sec-ch-ua-platform, user-agent, sec-ch-ua, sec-ch-ua-mobile, accept,
     sec-fetch-site, sec-fetch-mode, sec-fetch-dest, referer,
     accept-encoding, accept-language, priority
   Those requests were fetches, not navigations, so
   upgrade-insecure-requests and sec-fetch-user keep their http2 position
   (this is what the record's `header_order` expresses).

   c) the send path itself (H3Endpoint::request_headers) also read only
      `endpoint.header_order` and never `profile.header_order`, so even a
      correct Prepared still wrote the wrong order. It now falls back to the
      profile, mirroring the pseudo-header lookup.

   Tests: policy::tests::an_empty_http3_header_list_keeps_the_regular_headers,
   tests/fingerprints.rs::library_records_send_their_headers_on_http3 and
   the_http3_request_uses_the_records_header_order (the last one asserts the
   exact list `assemble_headers` produces, i.e. what goes on the wire:
   :method :authority :scheme :path sec-ch-ua-platform user-agent sec-ch-ua ...).

8. cross-check: NetLog's ClientHello vs the record
   `SSL_HANDSHAKE_MESSAGE_SENT` in the same NetLog carries a complete
   ClientHello record. Parsing it (18 extensions after dropping GREASE):

     0 5 10 11 13 16 18 23 27 35 43 45 51 4832 17613 51764 65037 65281

   The chrome160 record's `tls.extension_order` is the same set minus 4832 -
   no extension appears on one side only and not the other. So the
   tls.peet.ws capture and a local Chrome run agree, and 4832 is the single
   remaining gap.

   4832 payload is 0000 (server padding request, value 0). The bundled
   BoringSSL (btls-sys 0.5.6) exposes neither SSL_set_server_padding_request
   nor SSL_CTX_add_custom_ext, so there is no path to emit it; checked
   against ssl.h, ssl_lib.cc and extensions.cc. It stays a documented
   deviation, now with its exact payload recorded.

9. note: curl-impersonate's Chrome presets use a different HTTP/3 order
   The 48 presets in src/profile/generated.rs come from curl-impersonate and
   keep its data. For Chrome 150+ that data is

     sec-ch-ua, sec-ch-ua-mobile, sec-ch-ua-platform, user-agent, accept,
     sec-fetch-site, sec-fetch-mode, sec-fetch-dest, referer, ...

   whereas eight real Chrome 160 H3 requests send

     sec-ch-ua-platform, user-agent, sec-ch-ua, sec-ch-ua-mobile, accept,
     sec-fetch-site, sec-fetch-mode, sec-fetch-dest, referer, ...

   so the preset order is not Chrome 160's order. This is recorded here
   rather than silently "fixed": the presets are a faithful copy of the
   reference project's table, and editing them would make the library stop
   matching what it claims to reproduce. The chrome160 fingerprint record
   carries the measured order instead.

   Header counts per H3 target (from H3Endpoint::assemble_headers):
     chrome145/146/150/151/151_macos   17
     chrome152/152_macos               15
     firefox147                        15
     safari270                         12
     safari270_ios                      9
     chrome160 (record)                17

10. attempt: capture Chrome's QUIC ClientHello directly (did not work)
   `--origin-to-force-quic-on=quic.nginx.org:443` does make Chrome open QUIC
   connections, but every SSL_HANDSHAKE_MESSAGE_SENT in that NetLog is still
   a TCP ClientHello: QUIC handshake bytes go through
   socket_bio_adapter and are not logged as TLS handshake messages, and the
   forced runs ended in ERR_QUIC_PROTOCOL_ERROR. So the QUIC ClientHello
   cannot be read from NetLog with this Chrome build.

   The attempt did yield a second cross-check of the TCP handshake: that
   NetLog contains 11 distinct Chrome 160 ClientHellos, every one with two
   GREASE extensions and the same 18 non-GREASE extensions. Our live echo
   sends 19 extensions (2 GREASE + 17), so the same single 4832 gap shows up
   from three independent sources (tls.peet.ws capture, NetLog handshake
   bytes, live echo).

   The QUIC ClientHello is therefore checked structurally instead: the
   decrypted Initial carries key_share, ALPS, ECH GREASE, supported_versions,
   trust anchors, a non-empty transport-parameters extension and two GREASE
   extensions, which is the shape Chrome's QUIC ClientHello has.

11. note on the earlier probe attempts
   260 (H3_REQUEST_REJECTED) replies from quic.nginx.org are the nginx edge's
   per-source-IP application policy; identical requests succeed seconds later
   and the QUIC/TLS/H3 handshake completes every time.
