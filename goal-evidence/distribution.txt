# 依赖分发与 CI/CD 验证

日期：2026-11-12。验证机：Linux x86_64。

## 1. 下游依赖零配置（path 与 git）

根 `Cargo.toml` 不再有 `[patch.crates-io]`，三个定制依赖直接指向仓库内源码：

```toml
wreq = { path = "vendor/wreq", ... }
quinn = { path = "vendor/quinn", ... }
quinn-proto = { path = "vendor/quinn-proto", ... }
```

`vendor/quinn/Cargo.toml` 里的 `quinn-proto` 也改成 `path = "../quinn-proto"`。
`cargo metadata` 显示三个包都没有 registry source：

```
quinn 0.11.12        source=None  vendor/quinn/Cargo.toml
quinn-proto 0.11.19  source=None  vendor/quinn-proto/Cargo.toml
wreq 6.0.0-rc.31     source=None  vendor/wreq/Cargo.toml
```

独立消费者 A（path 依赖，`Cargo.toml` 里没有任何 `[patch.crates-io]`）：

```
$ cat /tmp/rci-consumer/Cargo.toml
[dependencies]
rust-curl-impersonate = { path = "/home/cc11001100/github/crawler-requests/rust-curl-impersonate" }

$ cd /tmp/rci-consumer && cargo run --quiet
profile=chrome150 target=chrome150
```

独立消费者 B（git 依赖，指向工作树快照的独立仓库）：

```
$ grep rust-curl-impersonate /tmp/rci-consumer-git/Cargo.toml
rust-curl-impersonate = { git = "file:///tmp/rci-git" }

$ cd /tmp/rci-consumer-git && cargo run --quiet
profile=chrome150 target=chrome150
```

两个消费者都重新编译了 vendored wreq/quinn/BoringSSL，说明源码分发本身可用。

musl 构建环境（Debian 的 musl-gcc 只有 C 驱动，BoringSSL 需要 C++ 标准库）：

```
CC_x86_64_unknown_linux_musl=zig cc -target x86_64-linux-musl     (wrapper)
CXX_x86_64_unknown_linux_musl=zig c++ -target x86_64-linux-musl   (wrapper)
CARGO_TARGET_X86_64_UNKNOWN_LINUX_MUSL_LINKER=<zig cc wrapper>
RUSTFLAGS=-C target-feature=-crt-static
```

wrapper 额外过滤 btls-sys 传下来的 `--target=x86_64-unknown-linux-musl`
（zig 的汇编器不认 Rust triple）。

## 3. CI/CD

- `.github/workflows/ci.yml`
  - `test`：`cargo test --workspace`
  - `consumer`：现场创建一个只有 path 依赖、没有 patch 的外部 crate，`cargo run`
  - `ffi`：构建 cdylib，启动本地 HTTP 服务，用 Python ctypes 调用并断言 200 与响应体
- `.github/workflows/release.yml`
  - `v*` tag 或手动触发；先跑全量测试
  - 矩阵：linux gnu x86_64/aarch64、linux musl x86_64/aarch64、macOS x86_64/arm64、
    Windows x86_64/arm64、Android arm64（后两个 `continue-on-error`）
  - 每个平台构建 `examples/echo` 与 cdylib，调用 `scripts/package_artifact.py`
  - 汇总 `SHA256SUMS`，用 `softprops/action-gh-release` 发布

两个 workflow 都已在 GitHub 上真实运行。v0.1.0 的 Release 运行 43088342862
包含 test + 9 个 build job + publish，全部 success；产物发布在
https://github.com/crawler-requests/rust-curl-impersonate/releases/tag/v0.1.0 。
CI 流程在 2398d4f 上运行 43088439998，success。

## 4. 回归

`cargo test --workspace`：库单元测试 29、`tests/api.rs` 10、`tests/fingerprints.rs` 19、
`tests/providers.rs` 15、`tests/wire.rs` 13、文档测试 2，共 88 条全部通过。

`tests/providers.rs` 共享进程级 provider 注册表，而 `refresh_providers()` 会重载
所有 provider；并行运行时 `a_failing_refresh_keeps_the_loaded_records` 注册的失败
provider 会让另一个测试的 refresh 偶发 `service unavailable`。测试改为通过
`exclusive()` 串行访问注册表后，连续 5 次运行 15/15 通过。

最后重新构建了宿主的 `cargo build --release --examples` 与
`cargo build --release -p rust-curl-impersonate-ffi`，并用改动后的工作树重新跑了
path 与 git 两个外部消费者，均输出 `profile=chrome150 target=chrome150`。

## 6. Release 产物运行校验

Linux（直接跑 Release 里下载的 `bin/echo chrome150 https://example.com/`，
aarch64 用 `qemu-aarch64-static`，gnu 加 `-L /usr/aarch64-linux-gnu`）：

```
x86_64-unknown-linux-gnu      exit=0  status: 200 OK
x86_64-unknown-linux-musl     exit=0  status: 200 OK
aarch64-unknown-linux-gnu     exit=0  status: 200 OK
aarch64-unknown-linux-musl    exit=0  status: 200 OK
```

ctypes 加载 Release 里的 cdylib（`bindings/ffi/python/demo.py`）：

```
宿主机 x86_64 gnu  .so   abi version: 1 / http status: 200
Alpine x86_64 musl .so   abi version: 1 / http status: 200
```

无法在本机执行的平台做了二进制级校验：

- macOS x86_64/arm64：`file` 为 Mach-O 64-bit executable/shared library，导出表里
  7 个 `rci_*` 符号齐全。
- Windows x86_64/arm64：`file` 为 PE32+ x86-64/Aarch64 DLL 与 EXE，
  `llvm-readobj --coff-exports` 显示 7 个 `rci_*` 导出。
- Android arm64：ELF aarch64，`readelf -Ws` 可见 `rci_*`，`DT_NEEDED` 含
  `libc++_shared.so`（消费方需随 APK 打包 NDK 的同名库）。

macOS/Windows/Android 尚未在真机跑 `echo`，属于剩余风险；Linux 四个目标已端到端
访问真实 HTTPS 站点。
