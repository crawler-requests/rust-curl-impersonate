Android request stacks — coverage, 2026-11-20

question
  "Can we emulate every Android request stack natively: the platform's own
  HttpsURLConnection, WebView, and the common libraries, across versions?"

the three stacks, and why one record each is not enough
  HttpsURLConnection / OkHttp 4.x  Conscrypt (platform) or OkHttp's own
                                   BoringSSL build; the shape changes with
                                   the Android release and with the app.
  WebView                          Chromium's stack. It is NOT desktop
                                   Chrome: a WebView 125 sends 17
                                   extensions with the old ALPS codepoint
                                   (17513) and padding, desktop Chrome 125
                                   sends 16 without either.
  Apps bundling their own stack    OkHttp, Cronet, or a pinned BoringSSL.

in the library, 15 Android records
  android_okhttp7..13    OkHttp 4 on Android 7/8/9/10/11/12/13
  android_confirmed      Confirmed Android app
  android_confirmed2     same app, second profile
  android_mesh / mesh1   Mesh Android app, h2 / h1
  android_nike           Nike Android app
  android_zalando        Zalando Android app
  utls_android11okhttp   OkHttp on Android 11 (uTLS)
  android_webview125     Android WebView 125

live verification, cipher list + extension set + Akamai fingerprint
against each record's own capture: 15 of 15 identical.
  (android_nike was the last holdout: its capture greases the key share
  but not the cipher list, and BoringSSL's single GREASE switch greased
  both. A cipher-only switch in the vendored BoringSSL fixes it - see
  below.)

new this pass
  android_webview125        captured from a real Android 13 runtime
                            (redroid, API 33). webview_shell has WebView
                            debugging on, so its DevTools endpoint reads
                            the echo JSON out of the page:
                              ja4    t13d1517h2_8daaf6152771_b1ff8ab2d16f
                              akamai 1:65536;2:0;4:6291456;6:262144|15663105|0|m,a,s,p
                            tools/capture/android_webview_capture.py
                            automates it.

  grease_skip_ciphers       SSL_CTX_set_grease_skip_ciphers keeps GREASE
                            out of the cipher list while the other lists
                            (group, version, key share, extension) still
                            carry it. That is what Nike's capture does,
                            and it makes android_nike Exact.

  device capture path       the redroid instance has root and tcpdump,
                            and `/system/bin/tcpdump -i any -w FILE
                            'tcp port 443'` over a fresh WebView load
                            yields a plaintext ClientHello. Useful when
                            the DevTools route is flaky.

gaps, stated plainly
  - Android 14/15/16 and OkHttp 5 are absent. Only one Android runtime is
    reachable (redroid13, API 33); pulling a newer redroid image failed
    (Docker Hub unreachable from the host).
  - There is no record for HttpsURLConnection itself. On Android it uses
    the same Conscrypt provider OkHttp falls back to, so the OkHttp
    records carry the shape, but the platform client was not captured on
    its own: app_process/dalvikvm cannot complete a handshake because
    Conscrypt's metrics hook needs a binder context that a bare process
    does not have (`SSLHandshakeException: null receiver`).
  - Apps that ship their own BoringSSL build (Cronet, some SDKs) each need
    their own capture.

device note
  Two stale network settings on the redroid instance made every capture
  fail: a global HTTP proxy at 192.168.1.23:8080 and an OUTPUT DNAT rule
  redirecting tcp/443 to 192.168.1.23:8081. Both targets are dead. They
  were cleared/removed to restore connectivity; the change is local to
  the test device.
