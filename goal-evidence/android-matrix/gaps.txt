android_okhttp7   t12d1208h2_d34a8e72043a_31a7e1922da8
  OkHttp on Android 7: TLS 1.2, 8 extensions, no status_request, and
  signature algorithms in sha512-first order - a generation older than
  every modern OkHttp build. Tried to reproduce it on Android 8.1 by
  disabling OkHttp's TLS extensions: the ciphers matched (d34a8e72043a)
  but the signature list stayed sha256-first and the ALPN and
  session_ticket extensions went missing instead. Its signature list also
  carries 0x0301 and 0x0303 (md5 and sha1 signatures), which no current
  TLS stack will offer, so the shape comes from Android 7's own BoringSSL
  and cannot be produced by any build that runs here. redroid publishes
  no Android 7 image (its oldest is 8.1).

  Reproduced byte for byte: OkHttp 3.12 capped to TLS 1.2 on an Android 8.1
  redroid container sent exactly this hello, all three segments equal

an Android-version difference worth naming
  OkHttp 3.12 on Android 13 sends no ALPN extension (t13d151100); the same
  build on Android 8.1 sends one, with h2 (t12d1209h2). So the ALPN gap is
  the platform's, not the library's, and android_okhttp3_12's t13d151100 is
  a true Android 13 observation. The Android 8.1 capture is the one that
  confirms android_okhttp8.

android_zalando     t13d1514h2_8daaf6152771_43ade6aba3df
  User agent okhttp/4.12.0. Against android_okhttp13 the only TLS
  difference is a signed_certificate_timestamp extension, and its HTTP/2
  settings differ (1:4096;3:4294967295;4:16777216;5:16384;...), so the
  app asked OkHttp for larger windows and for SCT.

  What the SCT request needs was located: Conscrypt's
  libconscrypt_jni.so exports SSL_CTX_enable_signed_cert_timestamps and
  SSL_enable_signed_cert_timestamps, and NativeSsl calls the latter when
  SSLParametersImpl.isCTVerificationEnabled(host) is true, with
  SSLParametersImpl.setCTVerificationEnabled(...) as the switch. Android
  10's platform Conscrypt (com.android.org.conscrypt) carries the same
  method.

  The probe reached that class and stopped there: the socket handed over
  is a Java8FileDescriptorSocket, and the nearest field of the right kind
  resolved to java.net.Socket's SocksSocketImpl, so the switch was invoked
  on the wrong object. Installing the bundled Conscrypt moved the failure
  one step on - OkHttp 4.12's Android10Platform refuses a bundled-Conscrypt
  socket in ConscryptSocketAdapter - and either way the request never
  reached a hello. That is a probe limitation at a specific step, not the
  absence of the capability.

  Everything else in the record matches the verified android_okhttp13
  hello.
