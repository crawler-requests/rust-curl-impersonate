iOS (and Android) request libraries — enumeration and version pools
date: 2026-11-20

the requirement
  "Cover every request library on iOS at every version, especially the
  newest, so a caller only names a library and the library picks.
  Then, one level up, support choosing versions by rule, e.g. a version
  pool that randomises."

what "every library" means on iOS
  iOS does not let an app choose a TLS implementation the way Android
  does; the platform gives it CFNetwork. So the library list collapses
  into stacks, not libraries:

    cfnetwork   NSURLSession, and Alamofire / AFNetworking / Moya /
                Combine / any hand-rolled URLSession call - all one
                ClientHello shape.
    webkit      WKWebView and Safari.
    cronet      Chromium's stack, only when an app ships it.

  The captures confirm two distinct shapes: Safari 16 offers 20 ciphers,
  an iOS app offers 13, and the app set is a strict subset. Emulating
  "Alamofire" therefore means emulating `cfnetwork`, not a library
  named Alamofire.

Safari 27.0 is covered, through the presets
  The captures here stop at iOS 26.0, but curl-impersonate's preset table
  ships Safari 26.0, 26.0.1 and 27.0 for both macOS and iOS. Those are now
  library entries too, so the newest Safari is reachable:

    entry_for_version("webkit", "27.0")       -> safari270_ios
    entry_for_version("webkit-macos", "27.0") -> safari270

  A pool over `webkit` contains them, and Client::from_pool builds from
  them. Verified live: safari270 and safari270_ios both send
  ja4 t13d2013h2_a09f3c656075_7f0f34a4126d with `Version/27.0` in the UA.

the enumeration layer (new)
  fingerprint::libraries()            ["webview", "conscrypt",
                                       "cfnetwork", "webkit"]
  fingerprint::versions(lib)          newest first, numeric ordering
                                      ("26.0" ahead of "18.5")
  fingerprint::newest(lib)            the newest record
  fingerprint::by_library(lib)        all records of one stack
  fingerprint::distinct_shapes(lib)   one record per distinct ClientHello

  A record now carries `library`, and iOS/Android records carry a real
  `version` rather than a profile name.

  Numbers today:
    webkit      12 versions (11.1 .. 26.0)   7 distinct shapes
                (includes Safari on iPad 15.6)
    webkit-macos 2 versions (15.6.1, 16.0)    2 distinct shapes
    webkitgtk   1 version  (26.4, Linux)      1 (partial: GnuTLS algorithms)
    cfnetwork    3 versions (13.0 .. 17.0)   5 distinct shapes
    conscrypt    7 versions (7 .. 13)        8 distinct shapes
    webview      1 version (125.0.6422.113)

why "distinct shapes" is the right unit
  Several Safari releases send byte-identical ClientHellos: 15.5, 15.6,
  16.0, 17.0 and 18.0 are one shape (t13d2014h2_a09f3c656075_14788d8d241b).
  A pool that randomly picks a captured record would therefore weight
  those years by how many captures were taken, not by how the browser
  looks. distinct_shapes keeps the newest representative of each shape,
  so 18.0 stands for the 15.5-18.0 group.

version resolution (new)
  fingerprint::for_version(lib, version)  -> the capture covering it
  fingerprint::covering_versions(lib, v)  -> which captures that shape came from

  A version is covered in three ways:
    1. an exact capture exists                       -> that record
    2. it sits between two captures of one shape     -> that shape
       (15.5-18.0 share one ClientHello, so 16.2 resolves to it and
        covering_versions() names 15.5,15.6,16.0,17.0,18.0)
    3. it is above the newest capture                -> the newest shape
       (27.0 resolves to the 26.0 record, and covering_versions() says so)

  A version between two DIFFERENT shapes (18.2 between 18.0 and 18.5,
  12.5 between 12.1 and 13.0) returns None. No capture describes it and
  the library will not invent one.

  Measured against the current set:
    11.1 exact, 16.2/17.3 -> 15.5-18.0 shape, 18.5 exact, 26.0/26.4/27.0
    -> the 26.0 shape, 12.5/13.4/15.0/18.2 -> None (gap between shapes).

one-call form (new)
  Client::from_pool(&pool) builds a client straight from a pool, so a caller
  writes neither a record name nor a Profile::find call:

    let pool = VersionPool::for_library("cfnetwork").with_rule(PoolRule::Newest);
    let client = Client::from_pool(&pool)?;

  An empty pool returns an error naming the reason ("no candidates").

the pool layer (new)
  VersionPool::for_library(lib)
      .with_rule(PoolRule::RandomShape | RandomVersion | Newest)
      .at_least("15.0").at_most("18.5")
      .pick()            -> Option<&Fingerprint>, usable as
                            Client::new(Profile::find(record.name())?)
  RandomShape   uniform over distinct shapes (default)
  RandomVersion uniform over captured records
  Newest        the newest capture

  tests/version_pool.rs covers enumeration, range filtering, shape
  collapsing, rule semantics and that a pool name resolves to a working
  Client.

honest gaps
  - There is no iOS 27 record. Safari 27.1/27.2 shipped, but tls-client
    v1.18.1 tops out at Safari_IOS_26_0 and uTLS at iOS 14; a real
    capture needs an iPhone or macOS host and this machine is Linux.
  - Intermediate Safari releases (15.0-15.4, 16.1-16.6, 17.1-17.5,
    18.1-18.4, 26.1-26.5) have no upstream profile. They are NOT
    invented: within 15.5-18.0 the shape is stable, so the covered
    shapes describe those years, but a version that changed its hello
    (as 18.5 and 26.0 did) is only represented where a profile exists.
  - tls-client's app profiles (ConfirmedAndroid, NikeAndroidMobile,
    ...) carry no OS version upstream (`Version: "1"`), so those
    records have an empty `version` and are addressed by shape instead
    of by a fabricated number.
  - Cronet remains uncovered; it needs a device capture.
